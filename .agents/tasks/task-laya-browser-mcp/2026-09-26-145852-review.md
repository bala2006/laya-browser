# laya-browser-mcp: local Laya decision engine layered on a Playwright-MCP superset (v1)

A greenfield TypeScript/Node 22 MCP server built in four commits. It ships two modes over one stdio server: an Assist mode that reimplements the Playwright-MCP ref/snapshot boundary in-house (an injected DOM walk that stamps `data-laya-ref="eN"`, since stable `playwright-core@1.63.0` exposes no public `_snapshotForAI`), and an Autopilot mode (`laya_run_goal`) that drives a snapshot → typed PageState → decision → execute loop with a local Laya narrow-question engine, a deterministic rule layer, and confidence-based escalation to the client LLM via MCP sampling. The whole product and its 51-test suite run with no weights (stubbed engine + local HTML fixtures); typecheck, build, and tests are green, and `pnpm run bench` reports 3/3 on the clean fixtures. The core `Decision` type is a discriminated union so a targeted operation without a target is unrepresentable.

Watch for: the benchmark's "100% per-step" is a subsequence match that does not penalize extra/wrong operations, so the headline slightly overstates precision (confirmed). The destructive-form guard keys off substring matching against goal-derived visible text and can fire on benign pages that merely mention a destructive word, or miss a destructive submit whose signal isn't in the captured text (confirmed, fail-safe direction). No other blocking issues found.

**Verdict**: APPROVED

## High-level view

The Assist/Autopilot split is clean: `BrowserSession` is the only module touching Playwright's launch API and owns the ref-resolution boundary, `src/laya/*` is the only place touching ONNX, and the decision/transition logic in the loop is separable from IO. Assist mode genuinely stands alone — no weights are loaded, refs resolve through the stamped attribute, and an unknown target falls back to a raw selector. This is verified by tests driving real headless Chromium.

The Autopilot loop does not trust a `DONE` decision. After the loop ends for any reason it re-captures the page and runs an independent marker check, reporting `verified` separately from the model's chosen operation; a rogue DONE-only engine test proves this. The design honestly requires an explicit success marker in the goal, and when none is present it reports "not checked" rather than claiming success.

The escalation boundary is sound. Sampling capability is probed via `getClientCapabilities().sampling`; when absent, `samplerFromServer` returns `undefined` and `escalate` degrades to a clear BLOCKED without throwing. LLM output is parsed through a balanced-brace extractor and every field is guarded — unknown operation, unresolvable target, or non-JSON all collapse to BLOCKED. Escalated confidence (0.75) sits above the default threshold (0.6), so there is no per-step re-escalation loop.

Safety guards run before the browser acts and fail closed: the domain allow-list rejects unparseable hosts when a list is configured and is enforced before `getPage()` in the navigate tool and before the initial goto in the loop; the destructive-form guard intercepts a CLICK before `execute()`. The guards are pure functions over already-captured state. Their weakness is precision, not placement (see below).

The state builder defensively enforces Laya's limits — controls capped at 20, option/name/value strings clamped, visible text and recent actions bounded, controls re-indexed 1..N while preserving refs — so the engine never hands `systemOne` an over-length option set. Licensing/attribution (MIT project, Apache-2.0 weights, CC BY 4.0 Mind2Web) and the honest positioning are all present and correct.

<summary>Issues (3)</summary>

1. **Benchmark step-accuracy overstates precision** — `stepAccuracy` (test/benchmark/harness.ts) is a subsequence match: it counts expected ops that appear in order but never penalizes extra or wrong ops, so "100% per-step" can hide superfluous steps. Consider reporting exact-sequence match or a precision term, or rename the metric to "expected-ops coverage."
2. **Destructive-guard false positives via visible-text match** — `checkDestructiveSubmit` blocks any auto-submit when `state.visibleText` matches the destructive keyword regex, which can trip on benign pages that merely mention "delete"/"remove" in body copy. Acceptable as fail-safe, but document it and prefer scoping the text check to text near the target control.
3. **Destructive-guard blind spots on Assist path and off-screen signals** — the guard only runs in the Autopilot CLICK path; the Assist `browser_type`/`browser_click` tools apply no destructive check, and a destructive submit whose signal isn't in the captured control names/visible text won't be caught. This is by design (Assist = human-driven), but the README should state the guard covers Autopilot auto-submit only.

<summary>Details</summary>

### Ref lifetime is snapshot-scoped

The in-page walk assigns refs monotonically in DOM order per capture, so a ref is only meaningful within the snapshot that produced it. Mutating tools return a fresh snapshot after acting, so a client that follows the snapshot-then-act flow always holds current refs — but a client that caches a ref across a mutation will resolve it against re-stamped attributes and may hit the wrong element. This matches Playwright MCP behavior; the README documents the flow. Ref resolution and the raw-selector fallback are both verified against `login.html` in `test/snapshot.test.ts`.

### The Autopilot loop verifies the final page independently

`verifyFinalPage` runs after the loop regardless of how it terminated (DONE, BLOCKED, max_steps, or a caught error path). It checks the goal's declared markers against the freshly captured final `title + visibleText`, returning `checked=false` when the goal declared no marker, and the summary distinguishes "reported DONE but the final-page verification FAILED." The rogue-DONE test drives an engine that immediately returns DONE with a goal whose marker the page never produces, and asserts `verification.verified === false` — it would fail if the loop trusted DONE, so it is a real guard, not a hollow assertion.

### Escalation boundary is guarded and never throws when sampling is unsupported

```
engine.decide → low confidence or BLOCKED?
                     │ no → execute
                     │ yes
                     ▼
             samplerFromServer(server)
                     │
       ┌─────────────┴──────────────┐
   undefined (no capability)     SampleFn
       │                             │
   BLOCKED (escalated=false)   parseDecision(raw, knownRefs)
                                     │
                        unknown op / bad target / non-JSON
                                     │
                                 BLOCKED
```

`parseDecision` extracts the first balanced `{...}` substring, so LLM prose around the JSON is tolerated (a test asserts `here: {...}` parses). Targeted operations whose `target` is not in `knownRefs` collapse to BLOCKED rather than executing against a phantom ref. `samplerFromServer` returns `undefined` when the client did not advertise sampling; the server wires a lazy sampler that throws only inside the `sample` callback, which `escalate` catches and turns into a BLOCKED note — so an unsupported client yields `outcome: "blocked"` with `source: "llm"`, asserted by the escalation test. Non-text sampling content returns an empty string, parsed downstream as BLOCKED.

### Safety guards fire before the browser acts and fail closed

`checkDomainAllowed` returns allow-all only for an empty list; with a list configured, an unparseable host is rejected (fail-closed), verified by both the pure-guard test and the `browser_navigate` test that asserts `session.launched === false` after an off-list URL — the guard rejects before `getPage()`. In the loop, the allow-list is checked before the initial `page.goto`, and the destructive-form guard is checked on a CLICK decision before `execute()` runs, with the delete/checkout fixtures asserting the page `#status` is unchanged afterward. These are literal DOM assertions that would fail if the guard were removed.

The precision caveats are the two issues above: the guard blocks on any destructive keyword found in `state.visibleText`, which is a coarse signal (a page whose body merely says "delete" would block a benign submit), and it only inspects captured control names + visible text, so a destructive action whose signal is off-screen or image-only slips through. Both err toward refusing rather than submitting, which is the right failure direction for an auto-submit guard, but the README's "inspects the target and its surroundings" undersells how broad the visible-text match actually is.

### State builder enforces Laya's limits defensively

The `head_max_len` guarantee is exercised, not just asserted: the test feeds 40 controls with 500-char names and confirms `buildState` yields ≤20 controls with ≤40-char names, contiguous 1..N indices, and clamped visible text. The engine builds the `target` choice keys from `controlLabel`, keeps a key→ref map, and degrades to BLOCKED (targetConfidence 0) when the model picks a key it cannot resolve — closing the phantom-ref path on the real-engine side too.

### Benchmark metric is optimistic

`pnpm run bench` runs the three clean fixtures with the stub and reports end-to-end success via the independent final-page check (correct) plus a per-step accuracy that is a subsequence coverage of the expected op list. Because it only checks that each expected op appears in order, a run that executes extra or wrong operations still scores 100% as long as the expected ops are present somewhere in order. The end-to-end success column is the trustworthy signal; the per-step number should be read as "expected-ops coverage," and the README/report line "100% per-step" carries more precision than the metric measures.

### Positioning and attribution are honest

The README leads with "fast local decision layer with an LLM fallback, not a magic autonomous agent," states the ~97.7% clean-form / ~1-in-5 real-site figures, and repeats that DONE is not proof of success. Licensing is correct and complete: MIT project code with a real MIT `LICENSE` file, Apache-2.0 weights attributed to Convai Innovations and not redistributed, and CC BY 4.0 Mind2Web attributed to Deng et al. (NeurIPS 2023) with the test set explicitly not redistributed. The web-agent export spike is recorded as VERIFIED with the tokenizer special-token rename caveat and the Python-sidecar fallback.
