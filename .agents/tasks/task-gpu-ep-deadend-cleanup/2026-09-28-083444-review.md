# Execution-provider auto-selection, dead-end fix, and single-loop cleanup (v1)

This branch does four things on the laya-browser-mcp Autopilot: it adds probe-verified onnxruntime execution-provider (EP) auto-selection so a GPU host uses CUDA/DirectML while everything still degrades safely to CPU; it breaks the escalation dead-end where a low-confidence BLOCKED plus an unreachable client LLM trapped a run; it collapses the previously flag-gated fast browser loop into the single always-on path and prunes the dead `LAYA_FAST_LOOP` / `LAYA_FAST_WAIT_CAP_MS` / `LAYA_CONFIRM_DESTRUCTIVE` knobs; and it corrects the docs to stop implying a sub-100ms local path, publishing a measured CPU decide median (~407 ms) with the GPU speedup labelled to-be-measured. The reorg is deletion-biased (~638 lines cut in the reorg commit) and the full offline suite passes (44 files, 318 passed, 3 skipped).

Watch for: (1) the collapse surfaced a real self-heal bug fix. The always-on fast path raises a soft `fast path: target is stale/covered/gone` error that the old `looksLikeStaleRef` matcher did not recognize, so the retry budget would not re-observe; the added regex closes it (confirmed). (2) The EP docs list `CUDA -> DirectML -> WebGPU -> CPU` as the auto-selection order, but the resolver never emits a WebGPU candidate; WebGPU is reachable only through the explicit override (confirmed doc/code mismatch). (3) `bestSafeProgress` always applies the destructive guard with `enabled=true`, so it is stricter than the loop when an operator disables the guard, which is the safe direction but an intentional asymmetry worth recording (confirmed).

**Verdict**: APPROVED

## High-level view

The EP resolver is a pure candidate-ordering function plus a probe-verified resolver that injects the load callback, so ONNX stays confined to `engine.ts` and the module imports no `ort`. Auto-selection is GPU-first and CPU-last, gated to the onnxruntime-node prebuilt matrix, and the probe IS the load: the first candidate that initializes wins and the model loads exactly once. A listed-but-broken EP throws and falls through; if every candidate fails the last error rethrows and `createEngine` degrades to `UnavailableEngine` rather than crashing.

The dead-end fix routes a low-confidence BLOCKED with an unreachable LLM to a non-destructive best-safe-progress step (the policy layer's next action, else a bounded targetless SCROLL_DOWN, else a preserved graceful BLOCKED). Every hard stop is intact: a confident BLOCKED never carries the resolver (so it still stops), the loop detector still terminates a no-progress run, and best-safe-progress never proposes a destructive CLICK or a phantom ref.

The loop collapse removes the `fastLoop` branch and its legacy `capture()/resolveRef/locate/probeSettle` twin, keeping the reviewed fast-path mechanics as the only path. The observable per-step decision behavior is preserved; the cost is that the old fast-vs-legacy parity tests could no longer A/B against a deleted path and were rewritten to assert the fast path's own behavior directly.

The flag pruning leaves no `confirmDestructive` / `fastLoop` / `fastWaitCapMs` references in `src/`, config is parsed once, and `types.ts` stays pure. The docs publish only a measured CPU number; the one accuracy gap is the WebGPU-in-auto-selection wording.

### EP resolution: probe-by-load, load-once, crash-proof fall-through

`candidateExecutionProviders(platform, arch, override?)` is a pure function: an explicit override collapses to exactly one verbatim candidate (auto-selection skipped, label inferred from the first provider); otherwise it emits a GPU-first list gated to the onnxruntime-node@1.30.0 prebuilt matrix (CUDA on linux x64, DirectML on win32 x64/arm64) and always appends a plain CPU candidate so resolution can never run out of options. `resolveEngine` then tries each candidate's injected `load` and keeps the first that resolves; a throw falls through to the next; if all throw, the last error rethrows so `createEngine` degrades to `UnavailableEngine`. Because the winning `load` returns the real handle, the model loads exactly once, with no probe-then-reload.

The crash-proof claim holds in both directions the briefing asked about. A listed-but-broken GPU EP (`ort.InferenceSession.create` throwing "DirectML unsupported by this model") is a `load` rejection, caught and continued; the all-fail path rethrows and `createEngine`'s `catch` returns `UnavailableEngine`. `test/execution-provider.test.ts` exercises exactly these: first-candidate reject falls to CPU, every-candidate reject rejects (so `createEngine` degrades), and the single startup log line names the engaged winner. The load-once guarantee is asserted (`load` called once on success, twice on one fall-through).

ONNX confinement holds: the resolver references onnxruntime only in comments and provider strings, and grepping `src/` shows no `ort` import outside `engine.ts`. The startup log in `src/index.ts` reads `engine.executionProvider` and guards for engines that do not expose it (the stub), so no ONNX detail leaks upward.

The doc gap: the code comment in `execution-provider.ts` is explicit that WebGPU is "not offered from auto-selection here (only via override)," but the README preference-order block, the provider table row (`WebGPU | experimental`), and docs/PLAN.md line 11 all present WebGPU as part of the auto-selection order. A reader following the docs would expect auto-selection to try WebGPU before CPU; it does not. The docs should mark WebGPU as override-only.

### Dead-end fix: best-safe-progress without weakening any hard stop

`bestSafeProgress(state)` resolves, in order: the policy layer's next non-BLOCKED action (a CLICK is only returned if it passes `checkDestructiveSubmit`), else a bounded targetless SCROLL_DOWN when the page still has controls or visible text, else `undefined` for a genuinely dead page. `escalate()` consults it only on the unreachable-LLM path and only after a non-BLOCKED Laya fallback fails to apply, so the T4 fallback still wins when Laya has a real guess. The loop wires the resolver in only for a `lowConfidenceBlocked` (`decision.operation === "BLOCKED" && lowConfidence`), which is the crux of the safety argument: a confident BLOCKED never receives the resolver, so `escalate()` degrades it to a hard BLOCKED unchanged.

The three hard stops are individually verified. A confident BLOCKED stops because the loop does not pass the resolver (test B models this by omitting `bestSafeProgress`, which is exactly what the loop does). A genuinely dead page yields `undefined` and stays BLOCKED (test C, unit and real-chromium). The loop detector still terminates a run whose only move is a page-non-changing SCROLL_DOWN (test C real-chromium bounds the transcript to the step budget). The phantom-ref concern is closed by construction: every returned decision either reuses a policy target already resolved against live controls or is the targetless SCROLL_DOWN.

The destructive-CLICK avoidance has a subtlety worth recording. `bestSafeProgress` applies `checkDestructiveSubmit` with the default `enabled=true`, whereas the loop's own guard uses the configurable `destructiveFormGuard`. If an operator disables the loop guard, best-safe-progress is stricter than the loop: it still refuses to propose a destructive submit and falls through to SCROLL_DOWN. That is the safe direction (the loop's guard remains the final authority on the eventual CLICK), but it is an intentional asymmetry the doc comment should name rather than leave implicit.

### Loop collapse: behavior preserved, parity tests necessarily rewritten

The reorg removes the `fastLoop` boolean and its legacy twin (the `capture()` / `resolveRef` / `locate` / `probeSettle` + `prefetchedSnapshot` path), leaving the atomic `captureFast` + `actOnNode` + `adaptiveWait` mechanics as the only path. The per-step decision pipeline is factored into `resolveStepDecision`, which returns escalation signals (`escalated`, `promptChars`) for the loop to meter rather than mutating counters inline. The observed decision sequence is the same rule-seed -> local-model -> confidence-check -> escalate flow as before.

The one real behavior change the collapse surfaced is a bug fix, not a regression. On the now-always-on fast path, a soft `fastAct` failure throws `fast path: target is stale/covered/gone (re-observe needed)`. The old `looksLikeStaleRef` matched only Playwright's native stale phrasings, so before this change a soft fast-path failure would not have been recognized as stale and the self-heal retry budget would not have re-observed; it would have propagated as a hard failure. The added `^fast path: target is (?:stale|covered|gone)` branch routes it back into the existing retry budget. The A1 reliability test was correspondingly strengthened to target the ref as the loop observed it this step (`refFor(state, ...)`) rather than a pre-captured ref, which is what actually exercises the always-on fast path's self-heal.

The cost of the collapse lands on test coverage: the old `test/fast-loop.test.ts` and `test/config.test.ts` blocks ran the same goal with `fastLoop` on and off and asserted the observed decision sequence and outcome were identical. With the legacy branch deleted there is nothing to A/B against, so those parity assertions were rewritten to assert the fast path directly (verified success, `actOnNode` taken over `locate`, speculative-reuse decide count, drift-discard). This preserves fast-path coverage but retires the cross-path identity guarantee. That is inherent to removing the branch, not lost coverage disguised as scaffolding removal, but the reviewer should confirm the identity guarantee is no longer needed.

### Flag and knob pruning

`LAYA_FAST_LOOP` (`fastLoop`), `LAYA_FAST_WAIT_CAP_MS` (`fastWaitCapMs`), and `LAYA_CONFIRM_DESTRUCTIVE` (`confirmDestructive`) are removed from config parsing, the config interface, the run-goal option surface, `server.ts` wiring, and the tool context. A grep of `src/` shows no dangling references, config is still parsed once, and `types.ts` remains free of playwright/onnx imports. `LAYA_FAST_WAIT_CAP_MS` becomes the internal `FAST_WAIT_CAP_MS = 200` constant used both as the adaptive-wait cap and the settle-probe timeout; a previously operator-tunable value is now fixed, which matches the de-nuance intent but is a surface reduction to confirm. The destructive-submit ask now follows the presence of a `confirm` callback alone (no separate opt-in flag), which is the R3 rationale the removed flag's doc comment already described.

### Docs honesty

The README and PLAN lead-ins now state the on-device decision is "one signal behind the 0.85 escalation gate, not a sub-100ms path" and publish a measured CPU decide median (~407 ms web-agent), with the GPU speedup labelled to-be-measured on the user's hardware and an explicit "we publish no GPU number we did not measure." No em dashes appear in the added lines of README, PLAN, or the script. The removed knobs appear in the docs only as historical context in the de-nuance ledger, not as live documented knobs. The one accuracy gap is the WebGPU auto-selection wording noted above.
