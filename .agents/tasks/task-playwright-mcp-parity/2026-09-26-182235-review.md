### Config is again the single engine-settings reader

`createEngine` now does `const env = config.env ?? {}` instead of `?? process.env`. Because the factory no longer falls back to the real environment, the resolution branches (`env.LAYA_ENGINE === "stub"`, `config.modelDir ?? env.LAYA_MODEL_DIR`, `config.cacheDir ?? env.LAYA_CACHE`) only ever see values a caller passed in.

Production supplies those values from the parsed config: `src/index.ts` calls `createEngine` with `engine: config.engine` plus conditionally-spread `modelDir`/`cacheDir`/`repo`/`subfolder`/`revision`/`executionProviders`. A scan for `process.env` across `src/` returns only the intended read at `config.ts:220` (the `loadConfig` default parameter); the two hits in `laya/index.ts` and the one in `index.ts` are comments. The v1 crack — a second module consulting settings env vars — is closed.

```
before:  config.ts parses env  ┐
                               ├─→ values could diverge if only one path set
         laya/index.ts re-reads┘   (process.env default)

after:   config.ts parses env ──→ index.ts passes resolved values ──→ createEngine
         (createEngine.env defaults to {}, read only in tests)
```

The four `createEngine` cases in `autopilot.test.ts` pass `env` explicitly (`{ engine: "stub" }`, `{ env: { LAYA_ENGINE: "stub" } }`, `{ env: {} }`, `{ modelDir: ... }`), so they still cover stub-forcing, env-driven stub selection, and the unavailable default — now decoupled from the ambient environment.

### FILL_FORM on escalation, guarded at the untrusted boundary

FILL_FORM joins the escalation `OPERATIONS` list and the prompt's JSON contract, but is *not* added to `TARGETED`, so it bypasses the single-`target` branch and hits a dedicated guard. That guard rejects a non-array or empty `fields`, any non-object entry, a missing/unknown-ref `target`, or a non-string `value`, returning `blocked()` in each case before constructing anything. Only a fully-valid batch produces a `FILL_FORM` Decision with a `FieldFill[]` and `source: "llm"`, so the parser can only emit the variant via the fully-validated path. SCREENSHOT and VERIFY remain excluded, with a comment explaining they are terminal/verification ops the loop reaches through its own terminal handling — so the fallback planner still cannot emit a run-ending op mid-goal.

The three new `escalation.test.ts` cases cover the meaningful boundaries: a valid two-field batch with known refs parses to a FILL_FORM whose `fields` match and whose `target` is undefined; a batch containing an unknown ref (`e99`) collapses to BLOCKED; and empty-list, missing-`fields`, and value-less-entry variants each collapse to BLOCKED. The unknown-ref and malformed-payload rejections are the ones that matter for keeping untrusted LLM output from constructing an illegal or unexecutable decision, and both are asserted.

### Regression surface

The FILL_FORM escalation path is reachable only when the engine escalates (low confidence); the deterministic rule layer still emits FILL_FORM locally for the common case, so the bench remains fully rule-resolved (login-multi 3 steps, `rule/laya/stub/llm = 3/0/0/0`, zero escalations). The escalation addition widens what the LLM *may* return without changing the local fast-path, so the measured "faster" behavior is unchanged. Full suite moved from 134→137 passed (the three new escalation cases), 3 skipped unchanged (real-weights gated), and typecheck/build stay clean.
