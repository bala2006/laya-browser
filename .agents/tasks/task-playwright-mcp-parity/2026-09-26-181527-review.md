# Playwright MCP tool-surface parity + faster Laya-driven Autopilot (v1)

This branch (`feat/laya-browser-mcp`, commits `69b12dc..80a611d`, FEAT-001..008) grows the existing Laya MCP server to full Playwright-MCP tool parity and broadens the local Autopilot so it drives that richer surface in fewer steps. The Assist surface is now a table-driven registry of 71 tools organized into CORE (always on) plus seven capability groups (NETWORK, STORAGE, TESTING, DEVTOOLS, PDF, VISION, CONFIG) gated behind `LAYA_CAPS`; `laya_run_goal` is preserved as the 72nd. `BrowserSession` is genuinely engine-driven (`chromium|firefox|webkit`) with engine selection confined to `src/browser.ts`. Part 2 broadens the Autopilot `Decision` union with HOVER, NAVIGATE_BACK, PRESS_KEY, FILL_FORM, SCREENSHOT, VERIFY and adds a deterministic rule that prefers a single FILL_FORM batch when the goal maps to ≥2 unfilled fields, cutting a two-field login from 4 transcript steps to 3 (25% fewer), fully rule-resolved with zero escalations. Typecheck, build, and the full offline suite are green (134 passed / 3 skipped, 20 files).

Watch for: a second module reads `process.env` for a setting (`src/laya/index.ts` re-reads `LAYA_ENGINE`/`LAYA_MODEL_DIR` even when config was already parsed), a mild dent in the "config parsed once" invariant (confirmed). The LLM escalation planner cannot emit FILL_FORM/SCREENSHOT/VERIFY — the broadened ops are only reachable via the local rules/engine, so a low-confidence multi-field goal loses the batch fast-path (confirmed). `browser_run_code_unsafe` is gated at the tool boundary only; `BrowserSession.runCode` (a raw `new Function` eval) is itself ungated (confirmed, low risk).

**Verdict**: APPROVED

## High-level view

Tool parity is delivered as real behavior, not stubs. Where a Playwright feature has a faithful headless analogue (tracing, highlight, route mocking, cookies/storage, vision mouse primitives, PDF) it is implemented against real Playwright APIs and the tests assert literal DOM/response outcomes. Where a feature is inherently interactive/codegen-only (video, codegen recording, inspector resume/annotate) the DEVTOOLS group returns an honest "not supported headless" message rather than faking success — a deliberate, documented divergence.

Capability gating is declarative and correct: the full toolset is a `REGISTRY` table, a tool with no `capability` is CORE, and a capability-tagged tool is simply not registered unless its capability is enabled. `assistToolNames` derives from the same table, and per-group tests confirm that enabling one group does not pull in another, so illegal (tool, caps) states are genuinely unrepresentable rather than being refused at call time.

Part 2 is real and measured. The FILL_FORM batch preference lives in both the deterministic policy layer and the StubEngine, reuses the same `applyFieldValue` logic as the `browser_fill_form` tool, and the benchmark harness plus the part-2 suite assert the step-count reduction and a zero-`llm` source breakdown against real Chromium. Graceful no-weights degradation is preserved (an `UnavailableEngine` still short-circuits to `degraded: true` with an empty transcript), and the `Decision` discriminated union keeps each operation's payload exact.

Boundary discipline mostly holds: `src/types.ts` is pure, Playwright is confined to `browser.ts`/`snapshot.ts` (the one `fill.ts` reference is an erased `import type`), and engine selection is a single map in `browser.ts`. The one real crack is a second `process.env` read in the engine factory.

The `run_code_unsafe` safety posture is fail-closed at the tool: off by default, still listed, refuses with a clear message unless `LAYA_ALLOW_UNSAFE_CODE=true`. The underlying session method that runs arbitrary code is not itself gated, which is acceptable given it is only reachable through that tool today.

### Capability gating via the REGISTRY table

`src/tools/registry.ts` + `src/tools/index.ts` model the whole surface as a `readonly RegisteredTool[]` where a missing `capability` means CORE. `isEnabled` is the single predicate, and both `registerAssistTools` and the derived `assistToolNames` filter through it, so the list a client sees and the tools actually registered can never drift. Enabling `LAYA_CAPS=vision` registers exactly the six mouse-xy tools and nothing from PDF or STORAGE; the network/vision/storage suites each assert both the positive membership and the negative cross-group exclusion. Because a disabled tool is never registered (not registered-then-refused), the illegal (tool, caps) state is unrepresentable at the MCP layer.

Measured surface: `assistToolNames([...all caps])` returns 71, `assistToolNames([])` returns 24 CORE, and `laya_run_goal` is registered separately for 72 total.

### Real behavior vs honest divergence in DEVTOOLS

`src/tools/devtools.ts` splits cleanly: `start_tracing`/`stop_tracing` write a real trace zip via `context.tracing`, and `highlight`/`hide_highlight` inject a real outline and report whether an element matched. The remaining nine (video chapters/actions, codegen recording, annotate, resume) route through `honestUnsupported`, which returns a text result naming what the interactive feature would do and why it has no headless analogue — never a faked success. The caveat: these return `isError: false`, so a client keying off `isError` sees a "success" with a no-op body. The descriptions state the limitation, but this is the one place where "parity" is nominal rather than behavioral.

### The FILL_FORM batch fast-path (Part 2)

The "faster" mechanism is concrete and lives in two consistent places. `policySeed` (`src/autopilot/policy.ts`, Rule 1a) and `StubEngine.decide` (Rule 2a) both compute `unfilledGoalFields` and, when ≥2 remain, emit one `FILL_FORM` carrying a `FieldFill[]` instead of N `TYPE_TEXT` steps. The loop's `execute()` applies the batch via the same `applyFieldValue` helper the `browser_fill_form` tool uses, so the deterministic path and the manual tool set a checkbox/combobox/textbox identically. Single-field goals deliberately keep the plain `TYPE_TEXT` path (Rule 1b), so they pay no batch overhead.

```
per-field:  TYPE_TEXT e_email → TYPE_TEXT e_pw → CLICK submit → DONE   (4 steps)
batch:      FILL_FORM [e_email, e_pw]           → CLICK submit → DONE   (3 steps)
```

`test/autopilot-part2.test.ts` asserts exactly one FILL_FORM with two fields, zero TYPE_TEXT, `actionSteps < 3`, and — critically — reads the live DOM (`#email`/`#password` `inputValue()`, `#status` textContent) so the test fails if the batch fill did nothing. The benchmark case `login-multi` additionally asserts `sourceCounts.llm === 0` and `sourceCounts.rule > 0`, proving every step was resolved locally.

### Discriminated union keeps illegal payloads unrepresentable

`Decision` in `src/types.ts` is a union where targeted ops carry a `target`, targetless ops carry none, PRESS_KEY carries a `key`, FILL_FORM carries `fields`, and VERIFY carries a `marker` — each variant forbids the others' payloads via `?: undefined`. The escalation parser upholds this at the untrusted boundary: any unknown operation, a targeted op with an unresolvable ref, or a PRESS_KEY without a key all collapse to a well-formed BLOCKED with `source: "llm"` rather than constructing an illegal object. The consequence worth flagging is scope, not soundness: the escalation op list omits FILL_FORM/SCREENSHOT/VERIFY, so the LLM fallback can never choose the batch — a low-confidence multi-field goal degrades to per-field typing.

### No-weights degradation and DONE-not-trusted

`runGoal` checks `engine.available` first and returns `{ outcome: "degraded", degraded: true, transcript: [] }` with an Assist-mode hint before touching the engine, so a missing bundle never crashes the loop; the part-2 suite exercises this with `UnavailableEngine`. Separately, DONE is never taken as proof: after the loop ends (on DONE, BLOCKED, or budget) `verifyFinalPage` re-captures the page and checks the goal's markers independently, and the summary explicitly reports "reported DONE but the final-page verification FAILED" when the model claimed success without it. VERIFY/SCREENSHOT are treated as terminal steps that end the run with a recorded result.

### ref-resolution ordering (prior bug lesson)

Every ref-based tool — click, type, hover, drag, drop, select_option, file_upload, fill_form, take_screenshot, the testing verify_* family, and devtools highlight — calls `await ctx.session.getPage()` before `ctx.session.resolveRef(...)`, each with the same explanatory comment. `resolveRef` is confirmed sync and throws when no page exists, so the ordering is load-bearing and uniformly applied. The Autopilot loop resolves refs without a per-op `getPage()`, but it calls `getPage()` once before the step loop, so a page is guaranteed.

### Cross-browser is genuinely engine-driven

`BROWSER_TYPES` in `src/browser.ts` maps the engine name to a Playwright `BrowserType`; nothing outside `browser.ts` selects an engine. `test/cross-browser.test.ts` runs the full sign-in flow on **firefox** (throwing loudly if firefox is not installed, so the guarantee is never silently skipped) and asserts the literal `Signed in as cross@example.com` outcome, proving it is not chromium falling through. WebKit is gated by `describe.skipIf(!webkitLaunchable)` after probing actual launchability (not mere file existence) — the honest reason the 3 skipped tests exist in this sandbox.

### Boundary discipline

`src/types.ts` imports neither Playwright nor ONNX (verified). Playwright is confined to `browser.ts`/`snapshot.ts`; the lone match elsewhere, `src/tools/fill.ts`, is an erased `import type { Locator }` with no runtime coupling. The one genuine crack: `src/laya/index.ts` reads `process.env` as the default env map and re-consults `LAYA_ENGINE`/`LAYA_MODEL_DIR`/`LAYA_CACHE` even though `src/config.ts` already parses them. Production wiring passes `engine`/`modelDir` from the parsed config so the effective values match, but a second module reading settings env vars weakens the "parsed once in config.ts" invariant and could diverge if only one path is set.

### run_code_unsafe safety

`browser_run_code_unsafe` is fail-closed: off unless `LAYA_ALLOW_UNSAFE_CODE=true`, still listed so clients discover it, and it refuses with a clear message otherwise (the safety suite covers both paths). The underlying `BrowserSession.runCode` builds an async function from the caller string via `new Function` and is not itself gated — the gate is enforced only at the tool. Reachable only through the gated tool today, so this is low risk, but the capability check ideally belongs closer to the eval site.

### Test quality

The suite drives real headless Chromium against local loopback fixtures and asserts literal outcomes throughout: mocked route JSON echoed by the page, offline `fetch` rejecting then succeeding, `mouse_click_xy` flipping `#status` to `clicked`, `mouse_wheel` moving `window.scrollY`, upload reflected in the DOM, dialog accept/dismiss changing the result, and the multi-field batch reflected field-by-field in `inputValue()`. These would fail if a tool were a hollow no-op. `verify_*` tools return PASS/FAIL with `isError` on FAIL. Real-weights Autopilot tests remain gated behind `LAYA_MODEL_DIR`.

Not tested: the DEVTOOLS honest-no-op tools are asserted only to return a message, not behavior (correctly, since there is nothing to observe headless); the escalation path's exclusion of FILL_FORM is not covered by a test asserting the degradation.
