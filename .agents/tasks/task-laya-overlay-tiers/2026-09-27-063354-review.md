# agentLens on-page overlay, headed-default browser, and autopilot narration (v1)

Adds a self-contained visual "agentLens" HUD (Tiers 1-4) that narrates what the autopilot is doing directly on the page, flips the browser to headed-by-default with a graceful headless auto-fallback for display-less environments, and threads step-by-step narration through the autopilot loop. The overlay is injected via `context.addInitScript` so it survives navigations and new tabs, and every overlay call is a guarded, never-throwing no-op so automation semantics and the `RunResult`/`StepRecord` shapes are untouched. ## High-level view

The overlay is one client script (a self-installing IIFE that builds a fixed-position, max-z-index, `pointer-events:none` root and exposes `window.__layaOverlay`) plus a server-side `BrowserOverlay` controller owned by `BrowserSession`. Injection through `context.addInitScript` is the key design choice: it fixes the old one-shot `highlight()` that a navigation wiped. Every server method funnels through a single `call()` that swallows all errors, so narration is strictly additive.

The headed→headless fallback is the load-bearing change for display-less environments. A headed launch that throws logs exactly one stderr warning (never stdout) and retries headless; a *headless* launch that throws still propagates as a real error. `effectiveHeadless` records what actually ran so `auto`-mode overlay resolves against reality.

Config parsing stays within boundary discipline: `overlay` and `autopilotWaitMs` are parsed once from env (with per-field override precedence), mode `auto` resolves `enabled = !headless`, `on`/`off` force it, the accent validates as hex with a fallback, and the wait is clamped to `[0, 5000]`. Nothing else reads `process.env` for these.

Loop narration goes through a `Narrator` facade that is entirely inert unless both an overlay and a page are supplied — which is what keeps the existing autopilot tests and the `RunResult` shape unchanged. The one wrinkle is upstream: the tool handler now acquires the page before `runGoal` runs its degraded short-circuit, so the browser launches on the no-weights path where it used to stay closed.

### Injection survives navigation; the client is self-contained and idempotent

The overlay's core problem — a `highlight()` that a navigation erased — is solved by registering the client script on the *context* via `addInitScript`, so every future document and new tab re-runs it, then also `evaluate`-ing it into the already-open page (init scripts only cover future loads). The client closes over nothing from Node (options are JSON-embedded), guards against double-install with `window.__layaOverlayInstalled`, and builds its root lazily via `ensureRoot()` with a `DOMContentLoaded` retry for the case where the init script runs before `<body>` exists. The re-injection is verified by the navigation test, which lands on a *different* fixture and still finds exactly one `#__laya_overlay__`.

### Overlay never intercepts clicks

The root and every child are created through `mkDiv`, which sets `pointerEvents: "none"` on creation, and the root itself repeats it. The click-safety test is the strongest evidence: it computes the banner's centre, calls `document.elementFromPoint` there, asserts the hit node is *not* inside the overlay, then fills and submits a real login form via the click tool and asserts the page reacted (`Signed in as ...`). That assertion would fail if any overlay node became hit-testable.

### Overlay never throws into automation

Every server method routes through `BrowserOverlay.call()`, which returns early when disabled or page-less and wraps the `page.evaluate` in try/catch; the in-page shim also re-checks `window.__layaOverlay` exists and wraps the method call. The mouse ops in `browser.ts` mirror the cursor/ripple *after* the real Playwright action, so a narration failure cannot pre-empt or alter the action. `highlight()` keeps its inline `data-laya-highlight-prev` outline in addition to the overlay spotlight, preserving the boolean contract and giving `hideHighlight()` something to clear even if the overlay is torn down mid-session.

One inconsistency worth noting (**possible**, cosmetic): `BrowserOverlay.refRect()` guards only `!page`, not `!this.enabled`, so it will `page.evaluate` even when the overlay is disabled. In practice `spotlight()` guards `enabled` before calling `refRect`, and the loop's `Narrator` only calls it when `on`, so there's no live path that hits a disabled `refRect` — but the method is inconsistent with the rest of the controller's "disabled ⇒ no-op" convention.

### Headed default with headless auto-fallback

```
launch()
  headless requested? --yes--> launch(headless:true); throw propagates (real error)
  headless requested? --no --> launch(headless:false)
                                   |
                                 throws? --yes--> stderr warn (once) + launch(headless:true)
                                   |                effectiveHeadless = true
                                 ok? --------------> effectiveHeadless = false
```

The asymmetry is correct: a headless failure is a genuine error and must surface, while a headed failure in a display-less sandbox is expected and recovers. The warning goes to `process.stderr.write` (never stdout), preserving stdio JSON-RPC integrity. `effectiveHeadless` is then used to resolve `auto`-mode overlay, so a forced-headless fallback correctly turns the `auto` overlay off, while a forced `on` still injects headless (which is exactly how the headless tests can assert the HUD). The fallback path is exercised directly by the "falls back to headless with no display server" test, which constructs `headless:false` and asserts a usable page comes back without throwing.

### Config parsing is once, typed, and never throws

`loadConfig` parses each overlay knob a single time with override-wins-per-field precedence. `parseOverlayMode` lower-cases and validates against `OVERLAY_MODES`, defaulting to `auto` on anything unrecognised; `parseHexColor` accepts `#rgb`/`#rrggbb` and falls back to `#a855f7` otherwise; `autopilotWaitMs` runs through `parseNumber` (which returns `undefined` for non-finite or out-of-range input) then `clamp`. Note the resulting behavior for out-of-range env values like `99999`: `parseNumber` rejects it, so the value becomes the **default 300**, not the clamped max 5000 — the config test documents this explicitly, and it's internally consistent (the clamp mainly guards override values). The `enabled` resolution (`on`→true, `off`→false, `auto`→`!headless`) is duplicated between `config.ts` (against the requested headless) and `browser.ts launch()` (against `effectiveHeadless`); this is deliberate so `auto` can re-derive after a fallback, and the config test plus the launch logic agree.

### Loop narration is inert without an overlay

`runGoal` builds one `Narrator(overlay, overlayPage)`; its private `on` getter requires *both* to be defined, and every method early-returns when off. Existing autopilot tests construct `runGoal` with no overlay, so they exercise the exact prior code path — confirmed by the end-to-end test that runs the same goal with and without the overlay and asserts identical `outcome`, `verification.{verified,checked}`, transcript operation sequence, and the `TYPE_TEXT` value. Narration is layered around, never inside, the decision/transition logic: `progress`+`thinking` before the decision, `uncertain`+toast on the escalation branch, `acting`+caption just before `execute`, `log` after each transcript push, and terminal `success`/`error` colouring with a `hideSpotlight` cleanup on every exit including the catch block. `DEFAULT_WAIT_MS` in the loop stays 500 as a bare-call fallback, but the server always threads `config.autopilotWaitMs` (300), so the effective default drops as intended.

### Eager page acquisition changes the degraded path

As originally written, `run_goal.ts` did `const overlayPage = await ctx.session.getPage()` in the handler before calling `runGoal`. `runGoal` returns early for the no-weights *degraded* case **before** its own `getPage()` call — so that path previously launched no browser. The eager acquisition meant invoking `run_goal` in an Assist-only/no-weights deployment launched a browser purely to return the degraded message (**confirmed** by reading the handler and the degraded short-circuit ordering). This pass fixes it: the handler now gates the page acquisition on `ctx.engine.available` and omits `overlayPage` (which the loop resolves for IO on its own) when the engine is unavailable, restoring the launch-free degraded path. This also directly serves the startup-efficiency goal — server boot never launches a browser (the session launches lazily on first `getPage`), and a degraded goal call no longer pays a browser-launch cost.

### Snapshot reflow tidy is behavior-preserving

`domWalk`'s `isVisible` now reads computed style first (short-circuiting `display:none`/`hidden`/`opacity:0`) before a single bounding-rect read, replacing a double forced reflow. Same element selection, fewer layout flushes; snapshot tests still pass.

### Tests assert real outcomes, not statics

The nine overlay tests force the overlay `on` so it injects headless, then read live DOM: banner text and computed `pointer-events`/`z-index`; that *every* node is `pointer-events:none`; re-injection after a cross-fixture navigation; the `elementFromPoint` + real-click hit-test; each driven API node's rendered position/text/colour (e.g. spotlight `left` = `rect.x - 4` = `36px`, cursor `left` = `120px`); the three state colours as exact `rgb(...)`; a non-empty headless `screenshot()`; the debug see-elements outlines cross-checked against actual `data-laya-ref` nodes; the with/without-overlay `RunResult` equivalence; and the headed→headless fallback yielding a working page. These would fail if injection, fallback, or narration were reverted. Not tested (acceptable given the display-less sandbox and opt-in defaults): the `typingEffect` per-character path, the `waitCountdown` ring rendering over time, and any genuinely-headed launch — all are opt-in or environment-gated.
