# Overlay UX fixes + blue brand accent (v1 review)

Fixes the four user-reported HUD defects on laya v3 and re-brands the accent from purple to blue. A headed Chromium launch now passes `--window-size` matching the fixed context viewport so the OS window stops rendering a grey strip on the right; the synthetic cursor is made visible at run start and a new four-corner "session frame" lights up for the run's duration; the streaming feedback banner moves from top-centre to a frosted-glass card at bottom-centre; and `DEFAULT_OVERLAY_ACCENT` becomes `#3b82f6`, with the old duplicate hardcode in `browser.ts` and the hardcoded purple rgba shadows in `overlay.ts` now derived from the accent. All four asks are addressed and the overlay invariant (every node `pointer-events:none`, `zIndex 2147483646`, every server method a guarded best-effort no-op) is preserved by the new nodes and methods.

Watch for: the `--window-size` value equals the viewport but a real OS window includes browser chrome, so the content area is slightly shorter than the viewport height — the horizontal grey strip is fixed but a thin bottom mismatch is *possible* (confirm by reasoning; not eyeballable here). The frame ON/OFF lifecycle is sound across both terminal paths (confirmed).

**Verdict**: APPROVED

## High-level view

The window-size fix is correctly scoped: the arg is built only for `engine === "chromium" && !headless`, and the headed→headless fallback re-launches without it, so firefox/webkit and every headless path (including the tests) are untouched and stay deterministic on the fixed viewport. The one residual question is that `--window-size` sizes the whole window including toolbar chrome, not the content area.

The two new overlay nodes and methods fit the existing pattern exactly. The session-frame container and its four corner children are all created through `mkDiv` (which forces `pointer-events:none`) and additionally set `pointerEvents:"none"` explicitly; `showCursor`/`sessionFrame` route through the same doubly-guarded `call()` helper that swallows all errors and no-ops without a page. The always-on cursor reuses the pre-existing cursor node (only flips `display`), so it introduces no new hit-target.

The frame lifecycle is symmetric: turned on once at run start, turned off in both the error `catch` and the normal return, with no early `return` in between that could leak it. The accent refactor centralises the colour in `config.ts` and derives rgba tints via an in-script hex→rgba helper with a blue fallback.

The tests genuinely exercise the new behaviour against real headless Chromium and would fail on revert (bottom-anchor assertion, frame existence, blue-accent assertion, corner `pointer-events:none`). No existing test was weakened; the accent literal updates are mechanical.

### `--window-size` scoping and the content-area caveat

The window arg is assembled as a spread-in object that is empty unless the launch is chromium *and* headed:

```ts
const headedWindowArgs =
  this.options.engine === "chromium" && !this.options.headless
    ? { args: [`--window-size=${this.options.viewport.width},${this.options.viewport.height}`] }
    : {};
```

Because it is only spread into the first `launch()` and the headed→headless fallback re-launches with `{ headless: true, ...launchOptions }` (no `headedWindowArgs`), the fallback never carries a stale window arg — the test run confirms this: the headed attempt launched with `--window-size=1280,800`, failed on the missing display, and the retry launched without it. Firefox/webkit never receive the Chromium switch. Headless paths, including both overlay test files, get an empty object and stay on the emulated viewport, so determinism is intact.

The residual concern is that `--window-size` sets the *outer* window dimensions. Chrome's tab strip + address bar consume vertical space, so the web content area ends up shorter than `viewport.height`. With a fixed Playwright context viewport the page still renders at the emulated size, which is why the horizontal strip (the user's actual complaint) is resolved; but if the goal is a pixel-exact window-to-content match, the height would need the chrome offset added. Not verifiable in this sandbox (no display), so flagged as possible.

### Session frame and always-on cursor preserve the overlay invariant

The frame is a fixed full-viewport container with four L-shaped corner children:

```
+--┐                        ┌--+
|                              |     each corner: two accent borders +
                                     accentRgba(0.55) glow, pointerEvents:none
|                              |
+--┘                        └--+
```

Both the container and every corner are built via `mkDiv` (which applies `pointerEvents:"none"`) and redundantly set `pointerEvents:"none"`. The invariant test walks `[root, ...root.querySelectorAll("*")]` and asserts zero nodes with `pointerEvents !== "none"`, so the new subtree is covered — and the new dedicated test additionally asserts every corner is `pointer-events:none`. `showCursor` only flips the pre-existing cursor node's `display` to `block` and seeds `__lastCursor` so the first `moveCursor` animates a trail from the centre rather than from `(0,0)`; no new node, no new hit-target.

`showCursor`/`sessionFrame` reach the page only through the same `call()` helper as every other overlay method, which no-ops on `!enabled || !page` and swallows any error from the injected call. Nothing new can throw into the caller or alter automation semantics.

### Frame lifecycle is symmetric across terminal paths

`narrator.sessionFrame(true)` fires once before the step loop; `narrator.sessionFrame(false)` fires in the `catch` block (error outcome) and again just before the normal return (done/blocked/stuck/max_steps). The only two `return`s reachable after the ON call are those two, both preceded by the OFF call, so no in-loop bail (`break` on stuck falls through to the normal return) leaks the frame. The early degraded-return for an unavailable engine happens before the ON call, so it is unaffected. The residual gap is only a hard process kill mid-run, which leaves the frame on the page until the next init-script re-injection — cosmetic.

### Accent centralisation and hex→rgba derivation

`DEFAULT_OVERLAY_ACCENT` is now the single source of truth (`#3b82f6`); `browser.ts` imports it instead of re-hardcoding `#a855f7`. Inside the injected script, `accentRgba(alpha)` parses `OPTS.accent` as `#rgb` or `#rrggbb` and falls back to blue `(59,130,246)` on a malformed value, replacing the two hardcoded `rgba(168,85,247,...)` purple shadows (spotlight ring, ripple fill) and feeding the new corner glow. The banner border also moves off the raw accent to a translucent white, consistent with the glassmorphism restyle.

### Tests are meaningful and unweakened

The bottom-anchor test asserts `bannerBottom > 0`, inline `top === ""`, `borderRadius >= 12`, a `blur` backdrop-filter, and an `rgba(` background, and that the hint moved to the bottom too — all of which fail against main's `top:10px` opaque bar. The frame/cursor test asserts the cursor is `display:block` after `showCursor` (before any `moveCursor`), the frame has exactly four corners, is visible, is `pointer-events:none` on both container and children, carries the blue accent (`59, 130, 246` in border/shadow), and hides again on `sessionFrame(false)` — none of which can pass without the new code. The accent literal changes in `config.test.ts`, `overlay.test.ts`, `tier3-ux.test.ts` are mechanical `#a855f7`→`#3b82f6` updates that keep the same assertions (including the invalid-value fallback now resolving to blue). No skip was added; webkit's cross-browser case self-skips on missing host libs as before.
