# Reliability, trust, perception, and observability for the Laya Autopilot (v1)

This change implements all four requested feature groups on top of the existing Autopilot: reliability (self-healing refs, a bounded settle probe, a loop/stuck guard), trust (secret redaction, an elicitation-backed confirmation hook, an opt-in Assist destructive guard), perception (an ARIA snapshot backend, snapshot diffing with delta prompts, viewport-priority ordering), and observability (a per-step replay export and MCP progress notifications). The design is consistently additive: every knob is a `LAYA_`-prefixed env var parsed once in `src/config.ts` and threaded inward as typed config, the pure decision logic stays IO-free, and the settle probe deliberately avoids `networkidle`/`slowMo`. Secret redaction masks only the displayed/logged echo while the real value is still typed into the page, and the destructive-confirmation hook preserves refuse-by-default when elicitation is unavailable. **Watch for:** the D1 replay artifact recording (a per-step PNG screenshot on every step) is wired **on for every production Autopilot run**, directly contradicting the "off by default, normal runs are not slowed" contract stated in the README, docstrings, and the orchestrator brief (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Reliability is layered cleanly onto the existing loop. Self-healing wraps each targeted action in a re-resolve-by-name+role retry; the settle probe is strictly observational and never touches the outcome; the loop detector adds a new additive `stuck` outcome. The one caveat is the breadth of the stale-ref heuristic, which treats an empty error message as "stale" and so may retry genuinely-failed actions.

Trust is well-guarded. Redaction is a pure module that captures actual typed secret values into a run-scoped set and masks them across transcript, overlay, logs, and the final snapshot while leaving verification to run against the real page. Confirmation is gated behind both an opt-in flag and an injected callback, with elicitation wired lazily and failing closed. The Assist destructive guard is opt-in and inert by default.

Perception is contract-preserving. The ARIA backend reproduces the same `Control[]` shape and re-stamps `data-laya-ref`, falling back to the DOM walk on any failure; viewport priority reorders the returned list while keeping `eN` stamps in DOM order so `resolveRef` stays correct; the diff is keyed by role+name because per-snapshot refs are not comparable.

Observability is where the contract slips. The progress-notification path is correctly no-op unless a `progressToken` is present. But the replay export enables per-step screenshot capture whenever the shared artifacts holder is present, and the server always supplies that holder — so recording is unconditionally on in production, not opt-in.

The CI workflow is a new, unrelated addition bundled into the same change set.

### D1 artifact recording is unconditionally on in production

The replay export is documented as pay-for-what-you-use: `RunGoalOptions.recordArtifacts` defaults to `false`, the loop only captures the per-step `page.screenshot({ type: "png" })` when recording is enabled, and the README states "Artifact recording is **off by default** so normal runs are not slowed; the export tool enables it." The `export_run` no-run message reinforces this: "laya_export_run enables per-step artifact recording for that run."

The wiring does not match. `run_goal.ts` derives the flag as:

```ts
const recordArtifacts = ctx.recordArtifacts === true || ctx.artifacts !== undefined;
```

and `server.ts` always constructs one holder and passes it into the `laya_run_goal` context (`artifacts` is set unconditionally, alongside a comment "Presence of the holder enables recording"). Because the holder is always present, `recordArtifacts` is always true for every real run, so every step pays for a full-page PNG screenshot plus the base64 encode and the per-step snapshot-text retention — exactly the cost the design claims to avoid, and a violation of the cross-cutting "additive, no slowdown" requirement.

There is no `LAYA_`-prefixed knob for this either, so an operator cannot turn it off. The export tool cannot retroactively enable recording for a run that already finished, so the current design *needs* recording on for the tool to have data — but that is a reason to make the enablement explicit (a config knob, or a two-call "arm then run" flow), not to leave it implicitly always-on while documenting the opposite. The test (`export-run.test.ts`) wires the holder directly and asserts artifacts were recorded, so it passes either way and does not catch the production always-on behavior.

### Self-heal retry classifies empty error messages as stale (A1)

`runWithSelfHeal` retries only when `looksLikeStaleRef(err)` is true. That predicate matches the expected Playwright stale/detached/timeout phrasing, which is reasonable, but it also returns true when `msg === ""`:

```ts
function looksLikeStaleRef(err: unknown): boolean {
  const msg = (err as Error)?.message ?? "";
  return (/Timeout|not (?:visible|attached|found|stable)|.../i.test(msg) || msg === "");
}
```

Any thrown value without a `.message` (or a non-Error rejection) is therefore treated as a stale ref, triggering a re-capture and re-resolve-by-name+role retry. In the self-healing direction this is mostly harmless — if re-resolution finds no match, the original error is rethrown — but when the same-named element still exists, a genuinely-failing action (e.g. an element that is present but perpetually not actionable for a non-stale reason) will be retried up to `maxRetries` and its real failure obscured behind the retry loop. The default retry count is 1, so the blast radius is small; worth confirming the empty-message branch is deliberate rather than tightening it to the known stale phrasings.

The A1 test is genuinely revert-sensitive: it rebuilds the target element to invalidate the captured ref mid-run and asserts both that the click ultimately lands (`#status` = "confirmed") and that `retries >= 1` is recorded, which fails if self-healing is removed.

### Settle probe stays observational (A2)

`probeSettle` is consulted only to set `StepRecord.settled` and toast "No change detected"; it never branches the decision path or outcome, and uses neither `networkidle` nor `slowMo` (its internal timeout is clamped to 0..2000ms). The A2 tests assert `changed=false`/`urlChanged=false` for a dead button, `urlChanged=true` for a navigating link, and `settled=false` on a no-op click step — all revert-sensitive.

### Loop/stuck guard adds an additive outcome (A3)

`stuck` is added to the `RunOutcome` union without altering any existing value; the synthetic terminal `BLOCKED` step is numbered `step + 1`, which is cosmetic since the loop breaks immediately after and does not collide with a real step. The A3 tests confirm a rogue always-same-CLICK engine bails as `stuck` before the budget with a trailing `BLOCKED` step whose detail contains "stuck", and that disabling detection lets the run exhaust `max_steps` — both revert-sensitive.

### Redaction masks the echo, not the keystrokes (B1)

The loop builds a run-scoped set of the ACTUAL values typed into secret-looking fields plus structural patterns (JWT, `Bearer`, `sk-`, AWS `AKIA`, GitHub `gh?_`, Google `AIza`, long hex/base64), masking them across transcript detail/value, `recentActions` (which feeds the next PageState and can reach the escalation LLM prompt), overlay narration, and the final snapshot. Verification runs against the *raw* final snapshot so redaction never weakens the success check. `redaction-loop.test.ts` asserts the transcript/render carry only the mask while `page.locator("#password").inputValue()` returns the real secret, and that `redactSecrets: false` opts out — revert-sensitive.

The `>= 40 char base64` and `>= 32 char hex` patterns are broad and will mask any long opaque token in snapshot text or details, including non-secret long identifiers. This is a deliberate fail-safe bias, not a defect, but it can surprise callers reading the transcript.

### Confirmation hook fails closed (B2)

When `confirm` is absent or `confirmDestructive` is off, the pre-existing refuse-by-default block is preserved exactly; only `confirmDestructive` true AND a present `confirm` callback escalates to inline approval, with any callback throw treated as a refusal. `confirmViaElicitation` gates on the client's advertised `elicitation` capability, treats only `action === "accept" && content.approve === true` as approval, and catches all errors into `false`. `confirmation.test.ts` covers approve → proceeds + note recorded, refuse → stays blocked + page unmutated, and confirm-absent → refuse-by-default, through the real loop.

### Assist destructive guard is opt-in and inert by default (B3)

`browser_click` runs `checkDestructiveSubmit` only when `ctx.assistDestructiveGuard` is true; when off (default) the handler is byte-for-byte the prior behavior — no snapshot, no guard. `safety.test.ts` asserts guard-on refuses and leaves the page unmutated, and guard-off (default) clicks and mutates — revert-sensitive on the backward-compat guarantee.

### Snapshot diff keys by identity, delta prompt is opt-in (C2)

`diffSnapshots` keys controls by `role + name` (per-snapshot `eN` refs are not comparable) and consumes duplicate identities positionally. The delta-only escalation prompt is sent only when `deltaPrompt` is on, it is not the first step, and the diff is non-empty; otherwise the full-snapshot prompt is used, and the delta prompt still lists current controls so a targeted ref stays resolvable. `snapshot-diff.test.ts` covers added/removed/changed/empty and the first-snapshot all-added case.

### ARIA backend falls back safely (C1)

Any failure obtaining the ARIA snapshot falls back to `capture(page, { backend: "domwalk" })`, so selecting `aria` can never harder-fail a capture than the default, and the backend re-stamps `data-laya-ref="eN"` so `resolveRef` is unaffected. `aria-backend.test.ts` verifies roles/names/options, unique/monotonic refs, ref resolution after an aria capture, and a full goal driving to `done` with `snapshotBackend: "aria"` — revert-sensitive against both the mapping and the ref-stamping.

### Viewport-priority ordering preserves ref correctness (C3)

The DOM walk stable-sorts the *returned* list nearest-first while leaving `data-laya-ref="eN"` stamps in DOM order, and `state-builder.ts` caps with `actionable.slice(0, maxControls)` in list order, so the ~20-control cap retains the nearest-viewport controls without affecting `resolveRef`. `viewport-priority.test.ts` confirms near-before-far when on, far-before-near when off, and that the far button's ref still resolves after reordering.

A default asymmetry to be aware of: `config.viewportPriority` defaults to `true` and `server.ts` threads it into the loop, so production runs reorder by viewport; but `RunGoalOptions.viewportPriority` itself defaults to `false` to preserve DOM order for the existing autopilot unit tests. The two defaults are intentionally different and each is exercised — worth confirming this split is deliberate rather than an oversight, since it means the loop's own default disagrees with the shipped config default.

### Progress notifications are no-op without a token (D2)

`onProgress` is wired only when both `extra._meta.progressToken` and `extra.sendNotification` are present; with no token, no sink, or no `extra`, no notifications fire and behavior is unchanged. `progress-notifications.test.ts` asserts emission with a token, silence without one, and no throw when `extra` is omitted — revert-sensitive.

### Unrelated CI workflow

`.github/workflows/ci.yml` is a net-new GitHub Actions pipeline (typecheck + build + test on Node 20/22, installing chromium/firefox with deps, pnpm `--frozen-lockfile`). It is reasonable and consistent with the repo's pnpm-lock standard, but it is orthogonal to the A/B/C/D feature work and is bundled into the same change set; reviewers should be aware it is here.
