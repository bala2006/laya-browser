# D1 replay recording made opt-in via LAYA_RECORD_ARTIFACTS (v2)

Re-review of the reliability/trust/perception/observability change set after the fix commit (`5e47b6d`) that responded to the v1 NEEDS_CHANGES. The fix introduces a typed `recordArtifacts` config knob (env `LAYA_RECORD_ARTIFACTS`, default false), gates per-step replay recording on that flag alone rather than on the presence of the shared artifacts holder, narrows the stale-ref heuristic so an empty error message is no longer treated as stale, and aligns the README and `export_run` messaging with the opt-in. The three blocking/actionable v1 findings are resolved end-to-end and the new regression test reproduces the original always-on bug. **Watch for:** nothing blocking; the CI workflow remains bundled in (informational, unchanged from v1) and the intentional `viewportPriority` default asymmetry is now documented in code (confirmed).

**Verdict**: APPROVED

## High-level view

The D1 always-on bug is fully closed. Recording now flows from a single `LAYA_RECORD_ARTIFACTS` knob parsed once in `config.ts`, threaded through `server.ts` into the run-goal context, and consumed in `run_goal.ts` as `ctx.recordArtifacts === true` — the holder's presence no longer participates in the decision. The loop populates `result.steps` and captures per-step screenshots only under that flag, so a default run pays for no extra screenshots. The regression test wires the holder exactly as production does but omits the flag and asserts the holder stays empty, which is precisely the case the v1 test could not catch.

The stale-ref heuristic now returns false for a message-less throw, so a genuinely-failed action with no error text is surfaced instead of being silently re-resolved and retried. The known Playwright stale/detached/timeout phrasings still trigger self-heal.

Documentation and the `export_run` no-run message now describe the explicit `LAYA_RECORD_ARTIFACTS=true` opt-in and state that a default run records nothing — matching the shipped wiring rather than contradicting it.

The v1 "worth confirming" items are addressed as documentation: the `viewportPriority` config-vs-option default split now carries a code comment marking it deliberate. The unrelated CI workflow is unchanged and remains a non-blocking call-out.

### D1 recording is now gated on the flag, not holder presence

The v1 defect was that `run_goal.ts` derived `recordArtifacts = ctx.recordArtifacts === true || ctx.artifacts !== undefined`, and `server.ts` always supplied a holder, so recording was unconditionally on. The fix removes the holder term:

```ts
const recordArtifacts = ctx.recordArtifacts === true;
```

`config.ts` adds `recordArtifacts` parsed via `envBoolDefaultFalse(env.LAYA_RECORD_ARTIFACTS)` (only the literal `"true"` enables it), `server.ts` threads `config.recordArtifacts` into the loop context while still passing the holder, and the loop gates every cost on the flag: the per-step `page.screenshot({ type: "png" })` runs only `if (recordArtifacts)`, and `result.steps` is emitted only `...(recordArtifacts ? { steps: artifacts } : {})`. The persist-to-holder branch in `run_goal.ts` is additionally guarded by `recordArtifacts && ctx.artifacts !== undefined`, so a default run leaves `artifacts.last` undefined and `laya_export_run` reports none recorded. This is genuinely opt-in end-to-end: knob → config → server → run_goal → loop screenshot + steps → holder (confirmed).

The regression test is revert-sensitive against the exact v1 bug. It constructs the holder the same way `server.ts` does but does not set `recordArtifacts`, runs a real goal, and asserts `artifacts.last` is `undefined` plus that the export tool reports "no autopilot run" and mentions `LAYA_RECORD_ARTIFACTS`. A companion test sets `recordArtifacts: true` and asserts steps are recorded with at least one `screenshotPng`. Under the old `|| ctx.artifacts !== undefined` wiring the first test would fail because the holder would be populated — so the test now catches what the v1 suite missed (confirmed).

### Stale-ref heuristic no longer retries message-less throws

`looksLikeStaleRef` now short-circuits `if (msg === "") return false;` before the phrasing regex, with a comment explaining that retrying an empty-message error would re-resolve and retry genuinely-failed actions and mask real failures. The known stale/detached/timeout phrasings still match and drive self-heal, so the A1 behavior (re-resolve by name+role, `retries >= 1`) is unchanged and the A1 test still passes (confirmed).

### Docs and export messaging match the shipped default

The README artifact-recording paragraph, the `laya_export_run` table row, the new `LAYA_RECORD_ARTIFACTS` env-var row, and the tool's no-run message and description all now describe the explicit `LAYA_RECORD_ARTIFACTS=true` opt-in and state that a default run captures no per-step screenshots and reports no recorded run. The v1 contradiction (docs claimed opt-in while wiring was always-on) is gone (confirmed).
